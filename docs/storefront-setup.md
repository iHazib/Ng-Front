# Public catalog integration — development setup

1. Open the **development** Supabase project already containing migrations 001–008. Do not select production or reset any database.
2. First run the entire READ-ONLY `supabase/sql-editor/07_preflight_public_storefront.sql` in a **new empty** SQL Editor query. Inspect private objects and receipt 009 rather than assuming a failed attempt rolled back. Only `prerequisite_008_present` should be true; every storefront object/function/trigger/receipt presence field must be false before installing. If anything is present, STOP and inspect that state; do not rerun. The API cannot inspect these private receipts. After confirming absence, use another **new empty** query and paste the ENTIRE `supabase/sql-editor/07_install_public_storefront_clean.sql`. Run once. Do not append, combine old/new lines or rerun earlier installers. The canonical installer file and distinctly named clean file contain identical bytes.
3. Its final `storefront_present`, `aliases_rls` and `search_rls` columns must all be `true`. The transaction adds public catalog/navigation RPCs, an admin-managed approved-alias table and a private indexed search projection with RLS enabled and no client policies. Direct client privileges remain revoked; the authorized table-owning SECURITY DEFINER RPCs read the projection. It does not publish or modify business records. There are no DROP, TRUNCATE, stock resets or deletes of business data. It populates and maintains its own private search index with upserts and adds audit/search triggers. Repeated installation is refused.
4. If SQL succeeds but PostgREST still cannot find the new RPC, run only `NOTIFY pgrst, 'reload schema';` in another query, then retry. Verify `public` is exposed in the API configuration and retain the explicit anon/authenticated EXECUTE grants included in the installer. Do not rerun the installer to repair a stale cache.
5. Local configuration uses existing `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Set `STOREFRONT_DATA_MODE=supabase` (also the default). No privileged database key is used by the storefront. Existing server-only Cloudinary settings and `MEDIA_ENVIRONMENT=development` support the synthetic media tests. No passwords or keys are needed in chat.
6. Run `npm run verify:storefront:development` against the local app on port 3000. It checks RPC availability **before** any fixture mutation. Only after this succeeds does it log in using the locally configured test-admin credentials, snapshot existing data, create synthetic catalog/taxonomy/media fixtures, verify public visibility, search/filters/options/images and admin-edit freshness, then hide fixtures and safely detach/clean their test media. It never imports or publishes real SKUs.

`STOREFRONT_DATA_MODE=sample-preview` works only with `next dev` and `APP_ENV=development`. It is explicitly isolated from the live catalog and rejected in production builds. The reference route remains development-only. Empty and unavailable database results never substitute sample products. No indexing, deployment, payment, order, blog or review integration is enabled in this stage.

Local database verification: the exact SQL Editor file is executed in a NEW disposable PostgreSQL database with migrations 001–008 by `scripts/test_database.py --storefront-installer`. Auth/Storage there are doubles. `npm run verify:storefront:mock-ui` uses an isolated mock RPC endpoint and real Chrome/Next rendering; its results must not be represented as actual provider verification.
